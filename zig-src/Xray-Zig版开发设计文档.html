0. 文档导读

本文档面向第三方实施团队，是 Xray-core 服务端 Zig 重写工程的完整开发设计依据。文档遵循三条主线组织：

  • 范围线（§1）：初期只实现 zig-src/xray.json 涉及的模块（VLESS+WS、VMess+KCP 两个入站，freedom 直连出站），但架构必须为后续追加模块预留挂载点（§9）；
  • 契约线（§4 + §5）：一切对外行为以本仓库 Go 上游源码为规范（Go 源码即 single source of truth），文档给出关键语义清单与逐字节线格式，避免二次解读偏差；
  • 验收线（§7 + §8）：上游有测试用例的模块，其 Zig 实现必须通过对应测试的移植版本；密码学层另有黄金向量（附录 A）锁定字节级正确性；最终以 Go 官方客户端互通为端到端验收。

实施前提：本仓库 D:\workspace\Xray-core-zig（或其交付副本）必须随文档一并移交——Go 上游源码是行为规范的最终裁决依据，本文档所有"对照上游"的引用均指向该源码树。Zig 实现代码将落在 zig-src/ 目录内，与 Go 源码共存于同一仓库。

1. 项目概述与范围

1.1 目标定位

是什么

用 Zig 0.17 重写 Xray-core 的服务端子集：单一静态 musl 二进制，运行在 F4610U 光猫（aarch64、Linux 4.1.25、512MB 内存）上，承接手机端 Xray 客户端的 VLESS/WS 与 VMess/KCP 两条代理链路，出站直连（freedom）。

不是什么

不是完整 Xray-core 移植：初期不实现 TLS/REALITY、路由规则、mux、sniffing、UDP 代理命令、DNS app、stats/API 等一切 xray.json 未用到的功能；也不是客户端——只做服务端（inbound）方向。

选型动机（与现状 Go 版对照）：Go 二进制在本设备上有体积大、启动内存高的问题（内核 4.1.25 上 Go 1.26+ 还有 32MB BSS 与 arm64 arena 映射两个已知雷区）；Zig 产 musl 全静态单文件、免 sysroot、体积可控，且 Zig 标准库自带全部所需密码学原语，无第三方依赖。

2.3 构建脚本与产物要求

// zig-src/build.zig（骨架示意，实施时按 zig 0.17 API 落地）
const std = @import("std");

pub fn build(b: *std.Build) void {
    const target_dev  = b.standardTargetOptions(.{});            // x86_64：dev/test
    const target_arm  = b.resolveTargetQuery(.{                  // aarch64 musl 静态
        .cpu_arch = .aarch64, .os_tag = .linux, .abi = .musl,
    });
    const optimize = b.standardOptimizeOption(.{ .preferred_optimize_mode = .ReleaseSafe });

    // 主二进制：xrayz
    const exe = b.addExecutable(.{
        .name = "xrayz", .target = target_arm, .optimize = optimize,
        .root_module = b.createModule(.{ .root_source_file = b.path("src/main.zig") }),
    });
    exe.linkLibC();                                              // musl（zig 自带）
    b.installArtifact(exe);

    // 单测（dev 目标原生跑）
    const tests = b.addTest(.{ .root_module = ... });
    const run_tests = b.addRunArtifact(tests);
    b.step("test", "Run unit tests").dependOn(&run_tests.step);
}
  • 优化级别：默认 ReleaseSafe（服务端处理不可信输入，保留越界检查；A53 性能足够）。可选 ReleaseSmall 产物做体积对照，交付默认 ReleaseSafe。
  • strip：发布产物 strip 符号（-fstrip 等价配置），预期体积 1–3MB 量级（对照：C 小工具 musl 静态 50–60KB，本工程含协议栈会大一个量级但远小于 Go 版）。
  • 等价命令行（不走 build.zig 的最小验证路径）：zig build-exe src/main.zig -target aarch64-linux-musl -O ReleaseSafe -fstrip -lc。
  • 产物自检：每次出 aarch64 产物必须 file 确认 statically linked、无 interpreter；在编译机上用 qemu-aarch64（若可用）冒烟，再上设备。

2.4 Zig 0.17 注意事项

  • zig 0.17 相对 0.13 是大改版：std.io 已被 std.Io 新 Reader/Writer 接口体系取代，不要照 0.13 时代教程写 IO 代码，以编译机自带 0.17.0 标准库源码为准；
  • JSON 解析用 std.json.parseFromSlice 并开启 .ignore_unknown_fields = true（对应 Go json.Unmarshal 默认忽略未知字段的行为，§4.3 依赖它）；
  • 密码学原语全部来自 std.crypto/std.hash（映射表见 §5.12），唯一需要手写的是 AES-128-CFB（约 40 行，基于 std.crypto.core.Aes）；
  • 线程：std.Thread.spawn 可指定栈大小；定时等待用 mutex+condvar 的 timed wait；
  • 随机数：业务随机（nonce/padding）用 std.crypto.random；测试里禁用全局随机（黄金向量要求确定性）。

3.3 模块注册与扩展机制

Go 上游靠各包 init() 副作用向全局注册表登记；Zig 没有这种机制，改用comptime 字符串表注册——所有模块在编译期显式登记，零运行时开销，且新增模块只需在表里加一行：

pub const OutboundFactory = *const fn (a: Allocator, cfg: *const conf.OutboundConfig) anyerror!Outbound;
pub const TransportFactory = *const fn (a: Allocator, cfg: *const conf.StreamConfig) anyerror!Transport;

pub const inbound_registry = std.StaticStringMap(InboundFactory).initComptime(.{

3.4 线程模型

表 3-1 线程模型（线程每连接，阻塞 IO + 超时驱动）
线程职责栈与数量
主线程配置加载、实例启动、SIGINT/SIGTERM 等待、优雅退出默认栈 ×1

KCP 会话线程每会话 1 个更新循环（Tti 间隔的 flush/重传/ACK 定时 + 空闲 30s 判定），与连接线程经有界队列交换数据96KB ×1/会话
自检线程§7.4 资源曲线：每 60s 读 /proc/self/{status,statm,fd} 输出一行 selfcheck（只读 /proc，零堆分配）默认栈 ×1

选型理由：个人代理场景并发量级在几十条以内，线程模型实现最简单、可验证性最好（无事件循环回调地狱）；KCP 的 Tti=20ms 定时精度线程模型轻松满足。空闲与超时全部用 SO_RCVTIMEO/SO_SNDTIMEO + 每操作刷新 deadline 实现，不需要独立定时器线程。

M24 线程账实测：空闲 4 线程；10 条保持连接 24 线程（4 + 2×10），M24 前为 34。
⚠️ 超时必须每轮重设，不能缓存：WS 的 reader/writer 是同一个 Session、底层同一个 socket fd，上行设 1s（切片轮询）与下行设 threshold(300s) 会互相覆盖；一旦「只在变化时 setsockopt」会导致会话永久阻塞（M23 实测全量测试卡死）。
⚠️ 调用线程栈必须 ≥512KB：连接线程兼任上行拷贝后，copyMain 内含 32KB 缓冲 + 协议体编解码，64KB 栈会溢出。

5. 模块详细设计

5.1 conf — 配置加载与校验

职责边界：读入 JSON 文件 → 解析为强类型配置结构 → 校验（含 §1.3 不支持项显式报错、§4.3 遗留字段容忍）→ 产出运行时配置对象。不做任何协议/传输语义。

  • 结构体字段名与 JSON 键逐字一致（streamSettings/kcpSettings/destOverride 等均为合法 Zig 标识符，直接同名映射，避免手写映射表出错）；
  • 校验规则逐条对照 infra/conf：listen 必须是 IP（域名监听报错，localhost→127.0.0.1）、端口必填、UUID 严格解析失败报错、vless decryption 必须非空且为 none、kcp mtu≥21、tti∈[10,1000]、cwndMultiplier≥1、maxSendingWindow≥mtu（GetSendingBufferSize()=MaxSendingWindow/Mtu 为 0 时报 "MaxSendingWindow must be at least Mtu"，对照 transport_method.go:578-580，不要求整除）、destOverride 枚举校验（enabled=false 也校验）；
  • WS 构建期处理照抄 transport_method.go:618-658：path 里 ?ed=N 剥离入 Ed 字段；headers 中不区分大小写的 "host" 键迁移进独立 host 字段（host 为空才生效）并从 headers 删除、打弃用警告；
  • KCP 默认值填充照抄 transport/internet/kcp/config.go：mtu 1350 / tti 50 / uplink 5 / downlink 20 / cwndMultiplier 1 / maxSendingWindow 2MiB——本配置显式覆盖前四项；
  • 产出物包含派生量（§5.10 的 InFlightSize 等）与两个入站各自解析完成的 StreamConfig。

5.2 core — 实例与生命周期

职责边界：按配置创建出站/入站 handler、控制启停顺序、持有全局资源（分配器/日志/统计钩子位）。对应 Go core.Instance + proxyman 的最小子集。

  • 启动顺序（对齐上游）：log 先就绪 → 创建出站（freedom 注册为默认）→ 创建入站（各自开监听线程）→ 打印启动日志；
  • 关闭顺序反演：先停 accept、再逐连接优雅关闭（发 WS Close/KCP Terminate、等 1s 半关闭窗）、最后释放资源；收到 SIGTERM/SIGINT 触发；
  • 配置错误：stderr 打印错误后 exit(23)；run -test：仅加载+校验，通过打印 "Configuration OK." exit(0)。

5.3 app/log — 日志

  • 行格式对齐 Go log 包 Ldate|Ltime|Lmicroseconds 前缀 + [Warning] 级别标签，例：2026/10/22 15:04:05.123456 [Warning] vless/inbound: invalid request version；输出 stderr；
  • 级别过滤在写入端做（severity≤配置级别才输出），warning 档实际输出 Error+Warning；
  • access 记录器：/dev/null 走文件打开（POSIX），"none" 走内建关闭；access 消息格式对照 common/log AccessMessage（本配置不落盘，格式对齐列为低优先级项）；
  • 线程安全：单互斥锁串行化写 stderr 足够（日志量低）。

5.4 app/policy + session — 会话与超时

  • Session 载体（每连接一份）：入站 tag/协议名、客户端源地址、用户 email/level、目标 Destination、超时值——对应 Go session 包字段的最小子集；入站协议名必须设置（vless/vmess），它是 freedom 内置默认规则的判定依据（§5.6）；
  • Policy：固定默认值（表 4-1），不实现 JSON policy 配置层；按用户 level 查表退化为恒返回默认；
  • 超时落点：VLESS/VMess 头阶段读超时=Handshake 60s；连接空闲=ConnectionIdle 300s（每成功读写刷新 deadline）；半关闭收尾=UplinkOnly/DownlinkOnly 1s。

5.5 app/dispatcher + outbound_manager — 分发

职责边界：把入站协议解出的 (Destination, Link) 交给出站。Go 侧 DefaultDispatcher 在本配置路径上退化为"直接 routedDispatch"（sniffing 关闭、无规则），Zig 实现其有效语义：

  • dispatch(dest, link)：从 outbound_manager 取默认 handler（第一个注册者=freedom "direct"）→ 调 freedom.process；
  • 预留 Router 接口位（返回 ErrNoClue 的空实现），将来接 app/router 语义（§9）；
  • Go 的 mux.Server 在本配置是纯透传壳（目的地址非 v1.mux.cool 即直通），Zig 直接不引入该层——入站 handler 直接持有 dispatcher；
  • 分发时写 access 日志（inTag >> tag 形态，对照 default.go routedDispatch 尾部），本配置落 /dev/null。

5.6 proxy/freedom — 直连出站

职责边界：按 finalRules 判定放行/黑洞 → 拨号目标 → 双向拷贝 → 超时与半关闭收尾。

finalRules 精确语义（对照 freedom.go）

  • 规则结构：action(allow=0/block=1) + networks（缺省=全部）+ port 列表（缺省=全部）+ ip 匹配器（缺省=全部；非 nil 时要求目标是 IP）；
  • 求值：用户规则按序取第一条 Apply 命中者；无命中再求值内置默认规则；
  • 内置默认规则（按入站协议名）：vless/vmess → 屏蔽私网目标 IP；其他入站 → 无默认规则；
  • 本配置效果：[{action:"allow"}] 无任何约束条件 → 匹配一切 → 永远命中用户规则 → 内置私网屏蔽永不生效 → 全局放行（含私网目标）。这正是该配置的意图：让手机客户端可以经代理访问内网；
  • block 语义（实现完整以备后续规则使用）：立即"接受"连接但不拨号，上行全丢弃，随机延迟 30–90s（blockDelay 可覆盖区间）后中断双向，日志 "blocked target"；
  • 私网匹配器：内置实现，完整清单照抄 common/geodata/consts.go:10-29 共 18 条：0.0.0.0/8、10.0.0.0/8、100.64.0.0/10、127.0.0.0/8、169.254.0.0/16、172.16.0.0/12、192.0.0.0/24、192.0.2.0/24、192.88.99.0/24、192.168.0.0/16、198.18.0.0/15、198.51.100.0/24、203.0.113.0/24、224.0.0.0/3、::/127、fc00::/7、fe80::/10、ff00::/8（注意是 ::/127 而非 ::1/128，覆盖未指定地址与环回；上游另有配套私网域名匹配器 lan/localhost 等，与本配置无关，不实现），不引入 geodata 文件依赖；
  • 域名预检：仅当存在带 ip 匹配器的规则时执行（偏差 D1）；AsIs 语义下拨号仍传域名由系统解析。

拨号与数据面

  • TCP 拨号：16s 超时、指数退避重试 5 次（基数 100ms）、成功后设 keepalive（idle 45s/interval 45s）；
  • 拷贝：link.reader → remote（上行）、remote → link.writer（下行），8KB 池化缓冲；空闲 300s 判死；客户端半关闭后 1s 收尾（UplinkOnly），远端半关闭后 1s 收尾（DownlinkOnly）；

KDF（密码学命门，黄金向量锁定）

// 上游 KDF 逐字（proxy/vmess/aead/kdf.go）——闭包嵌套 HMAC 构造，
// 不允许自行"等价改写"，Zig 实现以附录 A 黄金向量为唯一验收：
func KDF(key []byte, path ...string) []byte {
    hmacf := hmac.New(sha256.New, []byte("VMess AEAD KDF"))
    for _, v := range path {
        first := true
        hmacf = hmac.New(func() hash.Hash {
            if first { first = false; return hash2{hmacf} }
            return hmacf
        }, []byte(v))
    }
    hmacf.Write(key)
    return hmacf.Sum(nil)
}
// KDF16 = KDF(...)[:16]；盐常量见 aead/consts.go（共 9 个，全部列入实现）

实施红线：此函数用 Go 闭包把前一层 HMAC 当作后一层 HMAC 的内层哈希复用，语义无法从代码直观推导。必须采用"先跑向量生成器、再向量驱动实现"的方式：附录 B 的生成器已逐字复制上游逻辑并在编译机产出附录 A 的向量（全部自校验通过）；Zig 侧 kdf.zig 的单测逐字节比对这 8 组 KDF 输出，不一致即实现错误。禁止在无向量对拍的情况下宣布 KDF 完成。

响应头与数据面分块

  • responseBodyKey=SHA256(requestBodyKey)[:16]、responseBodyIV=SHA256(requestBodyIV)[:16]；
  • 响应头（38B）：内层**明文** {responseHeader, option, 0x00, 0x00}（TCP 时 command 为 nil 写两零字节；M8 互通修正：Go server.go:313-330 把 encryptionWriter 重指向普通 buffer，CFB 的 aesStream 只赋给 s.responseWriter 即响应体，内层不加密）→ 外层 18B AEAD 密封长度（盐 "AEAD Resp Header Len Key/IV"，AAD=nil）+ AEAD 密封载荷（盐 "AEAD Resp Header Key/IV"）；
  • 分块体（双向同构）：每块 [2B 长度][密文+16B tag]；长度明文或 SHAKE128 掩码（ChunkMasking，种子=对应方向的 bodyIV，每次取 2B 与长度异或）；AEAD=AES-128-GCM(bodyKey) 或 ChaCha20-Poly1305(密钥=MD5 级联 32B：key[0:16]=MD5(bodyKey)、key[16:32]=MD5(key[0:16]))；nonce=对应方向 IV 拷贝后把大端 u16 计数器写入前 2 字节逐块递增；
  • AuthenticatedLength(0x10)：长度段本身独立 AEAD 加密，两个方向均取请求侧材料——key=KDF16(requestBodyKey, "auth_len")，nonce 由 requestBodyIV 拷贝后大端 u16 计数器递增（上游 client.go:270-291 在响应方向同样复用 requestBodyKey/requestBodyIV，属 bug-compatible 的不对称实现，照抄、禁止"修正"为对称化，见 §4.4 D5；AEAD 类型随 security：AES128_GCM→AES-GCM、CHACHA20→ChaCha20-Poly1305，密钥同样从 requestBodyKey 派生）；GlobalPadding(0x08)：每块附加 SHAKE next()%64 随机填充；
  • 流终止：写 2B 零长度块（账号无 NoTerminationSignal 实验标记时）；
  • 防重放三件套：AuthID ±120s 时间窗、AuthID 120s 双池 map 去重、会话三元组（用户/key/nonce）3 分钟历史去重（30s 周期清理）；

6. 数据流 Walkthrough

6.1 VLESS over WebSocket（端口 19001）

  1. ① TCP accept

    监听线程 accept 0.0.0.0:19001 → 新建连接（SO_REUSEPORT 监听）→ 进入 WS 握手（读头超时 4s、头上限 8192B）。

  2. ② HTTP Upgrade 校验

    GET + Upgrade/Connection/Key/Version13 + Host==ltetp.tv189.com（大小写不敏感）+ Path=="/free" → 101（含 Sec-WebSocket-Accept）；任一失败按表 5-4 拒绝。

  3. ③ VLESS 头

    一次性预读（超时 60s）→ version=0 → UUID 清零 6/7 字节查表命中 pb8lpgli → addons 长度 0 → command=0x01(TCP) → 读 port+address（例 www.example.com:443）。

  4. ④ 响应头

    写 2 字节 {0x00,0x00} 并 flush。

  5. ⑤ dispatch

    dispatcher.dispatch(dest, link) → outbound_manager 默认出站 freedom "direct"。

  6. ⑥ finalRules 判定

    唯一规则无条件 allow 命中 → 放行（内置私网屏蔽被压制）。

  7. ⑦ 拨号

    16s 超时拨目标（域名 AsIs 直传）+ 指数退避重试 5 次 + keepalive(45s/45s)；失败关链路。

  8. ⑧ 双向拷贝

    上行：WS 帧(解 mask、拼接字节流)→freedom 写远端；下行：远端→每次写封一条 Binary 帧（不带 mask）；空闲 300s 判死；EOF 后 1s 收尾对向。

  9. ⑨ 关闭

    发 WS Close（正常关闭码）→ 关 TCP → 连接 arena 销毁、缓冲归还池。

6.2 VMess over mKCP（端口 19002）

  1. ① UDP 收包

    监听线程收 UDP 报文 → 切 segment → 取首段 conv → 查 (源IP,源端口,conv) 会话表；未命中且非 Terminate → 新建 KCP 会话（实现 Stream 接口）交上层。

  2. ② KCP 会话

    每会话一个更新线程（Tti=20ms）：发送窗口/重传/延迟 ACK(max(rto/2,20ms))/ping(5s)/空闲 30s 判死；收发窗口 ≈335 段、发送缓冲 1677 段（表 5-6）。

  3. ③ VMess AEAD 头

    读 16B AuthID → 逐用户 AES-ECB 解密 CRC 命中（±120s 窗口 + 防重放双池）→ KDF 派生两把头密钥 → GCM 解 18B 长度与 N 字节头载荷 → 校验 FNV-1a、security、command=TCP → 会话三元组入 3 分钟历史表。

  4. ④ 响应头

    SHA256 派生响应密钥 → 内层 4B 明文 → 外层 AEAD 双段共 38B 写回（M8 互通修正：内层不加密）。

  5. ⑤–⑧ 数据面分块

    上行每块：2B 长度（SHAKE 掩码，option 0x04）→ GCM 解密（nonce 计数器递增）→ 载荷交 freedom；下行反向分块加密后经 KCP 可靠传输；零长度块=流终止。

  6. ⑨ 关闭

    客户端关 → KCP SegmentOptionClose/CommandTerminate 状态机收敛（8s 强制）→ UDP 会话表清理 → arena 销毁。

  2. VLESS+WS 用例

    客户端配置 vless/ws/path=/free/host 头 ltetp.tv189.com 指向 127.0.0.1:19001 → socks 入口 → curl 抓取对照页、10MB/100MB 文件下载 md5 对拍、错误 Host/Path 得 404、半关闭语义、50 并发。

  3. VMess+KCP 用例

    客户端 vmess/kcp（mtu1250/tti20/双向20）指向 19002 → 同上数据面用例 + 人为 5% 丢包（tc netem）下仍收敛、重连 100 次、alterId=0。

  4. 负向用例

    错误 UUID、过期时间戳（>120s 偏移）、重放同一 AuthID（必须拒绝）、篡改头一字节（必须拒绝）、非 mux 客户端行为回归。

  5. 真机用例

    F4610U /tmp 隔离实例（29001/29002 端口），手机客户端测试配置直连；72h soak + /proc/statm 内存曲线 + 线程数/fd 数巡检。

7.4 验收 Checklist（交付门禁）

  • zig build test 全绿（含 §7.1 移植用例与 §7.2 向量用例）；
  • x86_64 互通四类用例全过（数据/关闭/负向/并发）；
  • aarch64 产物：statically linked、ReleaseSafe、strip、体积 ≤4MB（软目标）；
  • 真机 72h soak：内存无单调增长、无僵尸线程/fd 泄漏、watchdog 不复位（panic_on_oops=1 下零 oops）；
  • 自检日志（最小可观测性）：运行期每 60s 向 stderr 输出一行 2026/10/22 15:04:05.000000 [Info] selfcheck conns=N threads=M rss_kb=K fd=F，72h soak 的资源曲线即取自该行，读取 /proc/self/statm、/proc/self/status 与已建连接计数；
  • 与生产 Go 实例并存验证：隔离端口运行互不干扰，cutover 演练（停旧→起新→回切）有记录。

8. 开发里程碑规划

单人全职当量约 11–13 周；M1/M2、M4/M5 可并行压缩。每个里程碑验收不达标不进入下一个：

  1. M0 工程骨架与交叉编译链（0.5 周）

    build.zig + src/main.zig 骨架；x86_64 单测跑通；aarch64-musl 静态产物 file 自检 + 上光猫 /tmp 打印 hello；CI 式冒烟脚本。验收：产物 static、设备可执行。

  2. M1 公共基础层 + 密码层（1.5 周）

    common/{net,addr,uuid}；crypto/{kdf,cfb,chacha_key}。第一动作：跑向量生成器确认向量可复现，然后向量驱动实现 kdf/aead。验收：common/net 测试移植全绿 + 8 组 KDF 向量逐字节通过 + AES-GCM/CFB/ChaCha 自测。

  3. M2 配置层 + 日志（1 周）

    conf 全量解析校验（含忽略字段/不支持项报错/WS host 迁移/KCP 默认值）；app/log。验收：conf 测试移植（xray/vless/vmess/transport/freedom/loader/json reader 共 28 个用例）全绿；run -test 对 xray.json 输出 Configuration OK。

  4. M3 核心运行时 + freedom（1 周）

    core/{instance,registry,stream}、app/{dispatcher,outbound_manager,policy}、proxy/freedom（finalRules 全语义）。验收：配置→实例→监听→freedom 拨号链路打通（TCP 直通场景）；freedom_test 两例通过。

  5. M4 WebSocket 传输（1.5 周）

    HTTP Upgrade + RFC6455 帧子集 + Stream 适配。验收：ws 测试 2 用例移植通过；本机明文 WS 回显互通。

  6. M5 VLESS 入站（1 周）

    头编解码 + validator。验收：vless 3 用例 + VLESS 黄金向量通过；Go 客户端 VLESS+WS 全链路互通（curl/文件/关闭）。

  7. M6 mKCP 传输（2.5 周，最重）

    segment → ARQ（sending/receiving/RTO/AIMD）→ 会话状态机 → listener 会话表。验收：kcp 9 用例移植全绿；netem 丢包下回显收敛。

  8. M7 VMess 入站（1.5 周）

    aead 头解密封 + 防重放三件套 + 响应头 + 分块体（三种 option 位）。验收：vmess 13 用例（3 enc + 4 aead + 5 authid + 1 bench）+ 密封/响应向量通过；Go 客户端 VMess+KCP 全链路互通含丢包场景。

  9. M8 端到端与上机（1 周）

    互通四类用例全跑、aarch64 产物、光猫隔离实例部署、72h soak、资源基线记录、cutover 演练。验收：§7.4 Checklist 全项。

8.1 部署与回滚（上机操作规程）

  • 部署物：单文件 xrayz（aarch64 musl 静态）+ xray.json，放持久层（参照现行 Go 版布局 /opt/armbian/bin/xray/，UBIFS 剩余约 48MB，产物 ≤4MB 无压力）；二进制绝不能放 /tmp（tmpfs 写多少吃多少 RAM）；
  • 启动脚本：xrayz_start.sh 比照 xray_start.sh 形态——readlink /proc/pid/exe 精确单实例检测（禁止 cmdline 子串匹配）、nohup 拉起、pid 输出、日志追加 /tmp/xrayz.log；由 user_init.sh 开机调用，保持幂等；
  • 与生产 Go 实例并存：测试实例一律换端口（29001/29002）+ 独立日志与 pid，验证互不干扰后才谈 cutover；设备无 cron 看门狗拉起 xray（现行 Go 版也没有），Phase 1 不自建；
  • cutover 步骤：① 备份现网 Go 二进制与配置（留档 + md5）→ ② 精确 kill Go 实例并确认 19001/19002 释放 → ③ xrayz 先以隔离端口跑 10 分钟冒烟（自检日志行正常）→ ④ 切换配置端口为 19001/19002 重启 → ⑤ 手机客户端两条链路验证 → ⑥ 观察 24h 自检曲线；
  • 回滚：任一步失败立即 kill xrayz → 换回留档 Go 二进制重启（单文件回滚即换文件，客户端零改动）；cutover 后 24h 为回滚决策窗口，超窗回滚需重新评估；
  • 排障顺序：第一步 date 核时（VMess ±120s 时间窗），第二步 tail 自检日志行，第三步 netstat 端口与 pid 核对。

10. 风险与注意事项

R1 · 明文隧道现状：本配置 VLESS+WS+security:none 在线上是完全明文（这正是免流 Host 头伪装的既有形态）；mKCP 传输层在本 fork 已无加密，VMess+KCP 的机密性由 VMess 自身 AEAD 承担。Zig 版不改变该安全态势，但不要在文档外擅自给 VLESS+WS 加 TLS——那会破坏 Host 免流语义，属业务变更需业主单独决策。

R2 · 时钟敏感：VMess AuthID 时间窗 ±120s，设备时间漂移会表现为"invalid timestamp"批量拒绝客户端（与 REALITY 握手的时钟敏感同类）。部署/排障第一步先 date 核对；Zig 实现禁止放宽窗口。

R3 · 内存红线：设备真实空闲仅 5.9–8.7MB（弹性约 182MB）。KCP 默认 maxSendingWindow=2MiB/会话是最大变量——cutover 前建议显式调小（§3.5）；任何新缓冲分配都要过"每连接预算"评审。/tmp 放大文件会直接吃 RAM（tmpfs）。

R4 · 实施纪律：① 一切魔数照抄上游（表 4-1、表 5-6）；② KDF/AEAD 完成前禁止开始写 inbound 流程（先锁向量）；③ 每里程碑的"上游测试移植"是硬门禁，不允许"先跑通再补测试"；④ 发现文档与上游源码不一致，以源码为准并回记勘误——不要静默自行裁决。
