## 0. 结论摘要

文档的质量明显高于常见的"重写 XX"类方案：范围由真实 `xray.json` 锚定、契约以 Go 源码为唯一裁决、验收带硬门禁、有意偏差单列并标注风险。**可以作为外包合同的技术附件**。

支撑这一判断的最强证据是附录 A：我下载 Go 1.23.4 实际编译运行 `zig-src/tools/gen_golden_vectors.go`，输出与文档**逐字节完全一致**且 `SELF_CHECK PASSED`（记录见附录 A）。KDF、AuthID、密封请求头（124B）、响应头（38B）、VLESS 头全部可复现——这意味着"密码层先锁向量再写代码"这条路线是成立的，不是纸面承诺。

扣分全部集中在"逐字节级细节"上，而这恰是文档自己设定的标准。共发现 9 处需修订：**1 处 P0（会直接导致 VMess 分块体互通失败）、3 处 P1（行为描述与上游不符）、5 处 P2（出处/口径/计数）**。

## 1. 评审方法与可复现性

三类证据，按强度递减：

1. **密码学向量实测**：用 Go 1.23.4 编译运行同仓生成器，与文档附录 A 逐字段 diff。这是唯一能证明"文档数字不是编的"的方法。
2. **源码逐条比对**：对文档中带 `file:line` 的断言，回到仓库核对实际行号与语义；对不带行号的断言，反查源码定位。
3. **结构完整性检查**：测试函数名、测试数量、目录/包名、CLI 参数、退出码等可直接计数或 `ls` 验证的项。

未覆盖（诚实声明）：

- 表 2-1 的设备实测数据（真实空闲内存 5.9–8.7MB、内核 4.1.25 的 32MB BSS/arena 雷区）无法在本机验证，按"业主提供"采信。
- Zig 0.17 的 std API 仅抽验了版本真实性与命名（0.17.0 已于 ziglang.org 发布，master 为 0.18.0-dev），未逐条核对 `std.Io` 的 Reader/Writer 签名。
- 向量复现用的是 Go 1.23.4 而非文档所称 go1.27.1。二者结果一致，反证该构造在这两个版本间语义未变（`crypto/hmac` 的 FIPS 重构未改变可观测输出）。

## 3. 缺陷清单

### P0-1 · §5.8 AuthenticatedLength 的密钥与 nonce 方向写错，会直接导致互通失败

文档写："AuthenticatedLength(0x10)：长度段本身用 `KDF16(bodyKey,"auth_len")` 的 AEAD 独立加密"。

上游实际是 **bug-compatible 的不对称实现**——响应方向仍然取**请求方向**的 key 与 IV：

```go
// proxy/vmess/encoding/client.go:270-291（响应侧 reader/writer）
AuthenticatedLengthKey := vmessaead.KDF16(c.requestBodyKey[:], "auth_len")   // 注意：requestBodyKey
lengthAuth := &crypto.AEADAuthenticator{
    AEAD:           AuthenticatedLengthKeyAEAD,
    NonceGenerator: GenerateChunkNonce(c.requestBodyIV[:], ...),              // 注意：requestBodyIV
}
```

请求方向（`client.go:136-155`）同样用 `requestBodyKey/requestBodyIV`，所以两个方向**都用请求侧材料**。

**影响**：Zig 侧若按"对应方向的 bodyKey"实现（这是最自然的读法），服务端下行分块体在 `option` 含 `0x10` 时会全量解不开。本配置下客户端未开 AuthenticatedLength，所以互通测试**可能侥幸通过**，一旦客户端打开该选项即 100% 失败——属于最难排查的一类问题。

**修法**：把该行改为显式说明"两个方向均取 `requestBodyKey` / `requestBodyIV`（上游 bug-compatible 行为，禁止'修正'）"，并在 §4.4 偏差清单里加一条"此处照抄，不做对称化"。

### P1-1 · §5.6 私网 IP 匹配器清单漏 9 条

上游 `common/geodata/consts.go:10-29` 共 **18** 条规则，文档列了 9 条。缺失：`0.0.0.0/8`、`192.0.0.0/24`、`192.0.2.0/24`、`192.88.99.0/24`、`198.18.0.0/15`、`198.51.100.0/24`、`203.0.113.0/24`、`224.0.0.0/3`、`ff00::/8`；另 `::1/128` 上游实为 `::/127`。

**影响**：本配置被 `finalRules:[{allow}]` 压制，当前无影响；但文档 §9 明确把"加 block 规则"列为扩展点，按现文档实现会漏杀上述网段（含组播、文档保留段、CGNAT 之外的 198.18/15）。

**修法**：直接贴上游 18 行，或写明"完整清单以 `common/geodata/consts.go` 为准，本节仅举例"。

### P1-2 · §5.9 表 5-4 三个 HTTP 响应与 gorilla v1.5.3 实际行为不符

`go.mod:11` 锁定 `github.com/gorilla/websocket v1.5.3`，其 `Upgrader.Upgrade` 实际行为：

| 场景 | 文档写的 | 实际 |
|---|---|---|
| 方法非 GET | "其余 400" | **405** MethodNotAllowed |
| `Sec-WebSocket-Version` 不符 | 426 + `Sec-WebSocket-Version: 13` | **400** + 该响应头（头是对的，码错了） |
| Path/Host 不符 | 404，正文 `404 page not found\n`，`text/plain` | 404，**正文为空**（`hub.go:52,57` 是裸 `WriteHeader`，未走 `http.NotFound`） |

另外 gorilla 的检查顺序是 Connection → Upgrade → Method → Version → Key，文档表里的顺序不同；对实现影响小，但对"逐字节一致"的自测脚本有影响。

**修法**：按上表更正，并补一句"错误响应体为空，`Content-Length: 0`"。

### P1-3 · §5.7 "鉴权失败日志不含 UUID 明文"与上游相反，且未登记为偏差

上游 `proxy/vless/encoding/encoding.go:96`：

```go
return nil, nil, nil, isfb, errors.New("invalid request user id: " + u.String())
```

UUID **全串**会进错误日志。文档写的隐私加固方向正确，但它属于**有意偏差**，必须进 §4.4。否则实施方对照源码时会认为文档写错，或反过来把上游行为当 bug 修掉。

**修法**：§5.7 改为"与上游不同：仅记来源地址与长度，不记 UUID 明文（隐私加固，见 §4.4 D6）"，并在 §4.4 增行。

### P2-1 · §4.2 出处路径已不存在

文档引 `common/internet/system_dialer.go`，该包在本 fork 已不存在（`common/internet` 目录无此文件）。实际位置 `transport/internet/system_dialer.go:127`（16s）、`:103-107`（45s keepalive）。同类问题：§5.11 引 `common/net` 正确，但 `common/internet` 是旧版 v2ray 布局残留。

### P2-2 · §5.1 KCP 校验规则描述不准

文档写"maxSendingWindow/mtu 整除校验"。上游 `infra/conf/transport_method.go:578-580` 实为：

```go
if config.GetSendingBufferSize() == 0 {
    return nil, errors.New("MaxSendingWindow must be at least ", config.Mtu)
}
```

即 `maxSendingWindow >= mtu`（`GetSendingBufferSize() = MaxSendingWindow/Mtu`），**不要求整除**。按文档实现会拒掉合法配置（如 2MiB/1300）。

### P2-3 · 用例计数口径不一致

表 7-1 标题写"共约 53 个用例"，但按表内逐行相加：

`3(vless) + 3(vmess enc) + 4(aead) + 5(authid) + 1(bench) + 2(ws) + 9(kcp) + 28(conf) + 8(net) + 10(buf) = 73`

53 看起来等于"54 − 1（bench）"，即**未计 common/net 与 buf 两行**，但正文没说口径；§1.4 又写"约 50+ 个"。三处数字互不咬合。M7 的"vmess 16 用例"同样与表内 3+4+5+1=13 对不上。

**修法**：标题改为"共 73 个用例（其中 common 层 18 个为语义子集）"，并把 M7 的 16 改为 13。

### P2-4 · §7.1 中 `common/net` 计数错、§5.11 中 buf 测试数错

- `common/net/address_test.go` 实际只有 **2** 个 Test 函数（`TestAddressProperty`、`TestInvalidAddressConvertion`），文档写"5+2+1"，实为 **2+2+1=5**，合计 5 而非 8。
- §5.11 称"Go 侧 buffer/multi_buffer 等 **41** 个测试"，`common/buf/*_test.go`（7 文件）实为 **32** 个 Test 函数。

这两处不影响实现，但会让人怀疑其他数字的可靠性——建议一并改掉，或在文中标注"按上游 `go test -list` 口径统计"。

### P2-5 · §5.10 会话表键与写阻塞表述正确，但漏了「单报文多段」的边界

文档写"单个 UDP 报文可背靠背切出多段（KCPPacketReader 循环 ReadSegment）"——正确（`kcp/io.go`）。但没写**切分中途遇到非法段时，已解析的段是丢弃还是保留**。上游是整包丢弃（`listener.go:75-77`：`len(segments)==0` 才丢，说明解析失败的段不进列表但合法段仍处理）。这是丢包场景下的行为差异点，建议补一句。

## 4. 工程判断与风险（非缺陷，属决策建议）

### 4.1 线程模型：账算不过来

§3.5 的预算（50 并发 + 5 KCP 会话）自报 ≈ 20MB，而 §2.1 说设备**真实空闲 5.9–8.7MB**，靠 182MB 可回收页缓存兜底。2 线程/连接 × 50 = 100 线程 ≈ 6.4MB 栈，已经吃满空闲内存；KCP 最坏 12MB 无处安放。R3 只写了"建议调小 maxSendingWindow"，没给硬上限。

**建议**：把"2 线程/连接"改为"固定 worker 池 + 非阻塞拷贝循环"，或至少在验收里写死并发上限（如 ≤20 并发时 RSS ≤12MB），否则 72h soak 的"内存/线程/句柄在预算内"无法判定通过与否。

### 4.2 排期：偏乐观约 1.5–2×

11–13 周单人完成 WS 服务端 + 完整 KCP ARQ + VMess AEAD + VLESS + 配置层 + 测试移植。其中 M6 给 KCP 2.5 周（segment/ARQ/RTO/AIMD/四态机/会话表，且要求与 Go 逐字节一致），是全表最高风险项；M4 给 WS 1.5 周也偏紧（RFC6455 帧子集 + Stream 适配 + 握手错误码）。Zig 0.17 的 `std.Io` 迁移成本文档已自认，但没进排期缓冲。

**建议**：M6 拆成"segment+ARQ 可回显"与"RTO/AIMD/状态机对齐"两个门禁；总排期留 2 周缓冲，或把 M8 上机与 cutover 分开计价。

### 4.3 缺的章节

第三方团队接手会立刻问到的四件事，文档没有：

1. **错误与日志文案目录**：只说"对齐上游"，但没给消息模板表；`-test` 失败时 stderr 是英文原文还是中文，未定。
2. **资源上限**：最大并发连接数、fd 预算、accept backlog、UDP 会话表上限（`HubCapacity(1024)` 是否照抄）。
3. **部署与回滚**：启动脚本、与设备 watchdog 的关系、cutover 失败怎么切回 Go 版（§8 只有"演练"二字）。
4. **可观测性**：明确不做 stats（§4.4），但 72h soak 又要看内存/线程/fd 曲线——那这些数据从哪来？建议加一条"每 60s 打一行 `conns=N threads=M rss=K` 到 stderr"的最小自检日志，成本极低但能让验收可执行。

### 4.4 值得保留的设计

- §4.3 的"能解析即接受、不认识的键忽略、语义不支持的组合报错退出"三分法，边界清晰，比"尽量兼容"务实。
- §5.10 把 KCP 的"必须照抄的常量"列成表，是防止"按 RFC 直觉优化"导致不互通的正确做法。
- 附录 B 的向量重生成流程虽然土（pscp/plink 手工），但把"上游升级后如何重新校准"写清楚了，多数方案会漏这一步。
