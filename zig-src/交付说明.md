## 2. 设备部署（对照设计文档 §8.1）

> 硬约束：**二进制绝不能放 `/tmp`**（tmpfs，写多少吃多少 RAM）。参照现行 Go 版布局放 `/opt/armbian/bin/xray/`。

```sh
# ① 备份现网（留档 + md5）
cp -a /opt/armbian/bin/xray/xray      /opt/armbian/bin/xray/xray.go.bak
cp -a /opt/armbian/bin/xray/xray.json /opt/armbian/bin/xray/xray.json.bak
md5sum /opt/armbian/bin/xray/xray.go.bak /opt/armbian/bin/xray/xray.json.bak

# ② 上传新二进制并校验
#    scp zig-src/dist/xrayz-aarch64-musl root@<设备>:/opt/armbian/bin/xray/xrayz
chmod +x /opt/armbian/bin/xray/xrayz
md5sum /opt/armbian/bin/xray/xrayz     # 期望 9c49f55110f8e2bc8076af48db77eaec

# ③ 配置自检（不监听端口，只解析 + 校验）
/opt/armbian/bin/xray/xrayz run -test -c /opt/armbian/bin/xray/xray.json
#   期望输出：两条 DEPRECATED 警告（与上游同款）+ "Configuration OK."，exit 0
#   坏配置 exit 23（= 上游 config error 语义）

# ④ 隔离端口冒烟（复制配置，端口改 29001/29002，独立日志与 pid）
sed 's/19001/29001/; s/19002/29002/' /opt/armbian/bin/xray/xray.json > /opt/armbian/bin/xray/xrayz_test.json
/opt/armbian/bin/xray/xrayz run -c /opt/armbian/bin/xray/xrayz_test.json >> /tmp/xrayz_test.log 2>&1 &
sleep 70 && grep selfcheck /tmp/xrayz_test.log   # 应出现一行 conns/threads/rss_kb/fd
#   手机客户端临时改端口验证两条链路；确认无异常后 kill 测试实例

# ⑤ cutover：精确 kill Go 实例（readlink /proc/<pid>/exe 匹配，禁止 cmdline 子串匹配）
#    → 确认 19001/19002 已释放 → xrayz 用正式配置启动 → 手机双链路验证 → 观察 24h 自检曲线

# ⑥ 回滚：kill xrayz → 换回 xray.go.bak 重启（单文件回滚，客户端零改动）
```

**启动脚本要点**（沿用现行 `xray_start.sh` 形态）：`readlink /proc/$pid/exe` 精确单实例检测、`nohup` 拉起、pid 落盘、日志追加 `/tmp/xrayz.log`、`user_init.sh` 开机调用且幂等。设备无 cron 看门狗（现行 Go 版也没有），本版不自建。

## 3. 运行时行为（运维可见面）

| 行为 | 说明 |
|---|---|
| 启动日志 | `XrayZ 0.1.0 started`（Info） |
| 自检行 | 每 60s 一条：`2026/10/23 14:49:45.382000 [Info] selfcheck conns=0 threads=4 rss_kb=7784 fd=7`（§7.4，72h soak 的资源曲线取自该行） |
| access 日志 | 与上游同形：`from 1.2.3.4:5678 accepted tcp:host:443 [kcp-vmess >> direct] email: xxx`；KCP 会话的 from 为会话对端 `IP:port` |
| 鉴权失败 | access rejected + warning `invalid request from <src>`；**不落 UUID 明文**（D6） |
| 并发上限 | 默认 **256**（`buf.Policy.max_concurrent_conns`；**0 = 不限**）。上游对入站 TCP 无硬上限，256 是设备资源安全阀（已登记自定策略）。超限直接关闭 + warning `rejecting connection from <src>: concurrent connections exceed limit 256 (active=NNN)`（TCP 与 KCP 会话面同规则）。M12 实机教训：曾设 64 → 地铁弱网重连风暴被拒 7244 次 |
| Mux 服务端 | 支持 VLESS/VMess 的 `command=3`（v1.mux 帧复用）；日志 `mux session opened/closed: id=… dest_port=… from=…`。**响应帧恒为 Keep**（上游 `NewResponseWriter` 语义），access 记录真实目标而非 `v1.mux.cool` |
| 关键节点日志（排障期，M12 起） | `connection closed: from=… tag=… transport=… protocol=… duration=…ms`（短命连接=重连风暴证据）；`kcp session opened/closed: conv=… duration=…ms`；握手读失败 `vless/vmess handshake read <err> from <src>`；`ws handshake dropped (read/parse failure) from <src>` |
| TCP_NODELAY | accept 与 dial 两侧均 `setsockopt(TCP_NODELAY, 1)`，对齐 Go `net.TCPConn` 默认（无 Nagle）。缺此项时高 RTT/丢包下小包被压到 ACK 返回才发，体感等同"丢包" |
| 退出 | SIGINT/SIGTERM → 停 accept → 强制终结 KCP 会话 → 等连接收敛 → exit 0（实测 < 1s；KCP 不走 8s Terminate 握手） |
| 日志级别 | 默认 `warning`（`xray.json`）；调 `info` 可看启动/自检/access |

### 4.6 soak 资源曲线（M25）

设备无 python3，流程是「下载日志 → 本地分析」：

```sh
# 打包机（或任何能连设备的地方）下载
python bm_pull.py /tmp/xrayz.log .temp/dev_xrayz.log
# 本地
python3 zig-src/tools/soak_report.py -f .temp/dev_xrayz.log --mb
```

输出 min/max/avg/p95、前后半段泄漏判定、§3.5 门限对照；退出码 0 = 无告警。
参数：`--tail N`（只看最后 N 个采样）、`--since '2026/10/24 08:'`（按时间过滤）。

M27 实测（4.6 小时、256 采样、真实流量峰值并发 66）：threads 138、fd 151、
RSS 峰值 8.48MB、0 崩溃 / 0 拒绝；前后半段 RSS +13.4%（绝对 +137KB）无泄漏趋势。

⚠️ **门限判定随并发自适应**（M27 起）：§3.5 平板门限（线程 ≤60 / fd ≤150）是 20 并发稳态口径，
高并发下必然超。工具改用模型预算 `2×峰值并发 + 余量`（threads +8 / fd +24），超平板但在预算内
记 PASS。另注意 selfcheck 的 conns **不含 mux 子会话**，高复用下预算偏紧，余量已按实测标定。

## 6. 已知偏差与限制

### 6.1 有意偏差（设计文档 §4.4，已确认）

| # | 偏差 | 影响 |
|---|---|---|
| D1 | freedom 仅在存在带 ip 匹配器的规则时才做域名 DNS 预检 | 本配置 `[{allow}]` 恒跳过预检，少一次 DNS 查询，决策等价 |
| D2 | access=/dev/null 在非 POSIX 平台映射为丢弃 sink | 生产 Linux 无差异 |
| D3 | freedom 下行不做 splice 零拷贝（用户态 8KB 拷贝） | A53 上非瓶颈 |
| D4 | CLI 只支持 `run -c/-config` + `-test` | 运维面收敛 |
| D5 | VMess AuthenticatedLength 两方向均用请求侧材料（bug-compatible） | 与上游互通必需，**禁止"修正"** |
| D6 | 鉴权失败日志不落 UUID 明文 | 隐私加固；排障少一条定位信息 |

### 6.2 实现级登记（与上游行为差异，已评估）

| 项 | 说明 |
|---|---|
| WS 响应无 `Date` 头 | gorilla 有；字节级断言需忽略该头（M4） |
| WS 帧载荷上限 1MiB | 超限回 Close 1009（上游无限读的 DoS 加固，M4） |
| KCP 停机强制终结 | 跳过 8s Terminate 握手直接 Terminated（上游进程直接退出，等效） |
| KCP 会话 access 日志来源 | 用会话对端 `IP:port`（上游记 udp 地址串） |
| 并发上限 64 + overload 日志 | 上游无此能力，按 §3.5 新增 |
| selfcheck 日志行 | 上游无此能力，按 §7.4 新增 |

### 6.4 开机自启（M21 已修复）

**历史问题**（M20 发现）：设备重启后跑的是 Go 版，`xrayz-start.sh` 只是手工脚本，
`user_init.sh` 内无 xrayz 项——M20 上机前设备已静默回落到 Go 版，等于"线上 Zig"名不副实。

**现状**：`/opt/script/xray_start.sh` 已重写为 **Zig 优先 + 失败回退 Go**（`user_init.sh` 第 5 步
调用它，路径不变）：

1. 任一版本已在跑 → 不动（幂等，`readlink /proc/$pid/exe` 精确比对）
2. 两版都没跑 → 起 `xrayz` → **冒烟**（进程在 + 19001 TCP + 19002 UDP 都在听，最多等 3.6s）
3. 冒烟通过 → 用 Zig 版；任一条件不满足 → 停 xrayz，回退 Go 版（原逻辑）
4. `xrayz` 未安装 → 直接走 Go

旧脚本备份：`/opt/script/xray_start.sh.bak.m21`（md5 `1a2b394f976819b6db5fb60da5b86193`）。
三分支已隔离验证（幂等 / Zig 起不来→回退 / xrayz 不存在→Go）。

**注意**：`/opt` 是 overlay（upperdir=`/opt/cu/apps/apps`，UBIFS），脚本与二进制改动持久；
`/tmp` 是 tmpfs（日志重启即丢，属预期）。

## 7. Phase 2 清单（按收益排序）

5. **TLS/REALITY**（需先有服务端 TLS 栈；注意 R1：不得擅自给现有 VLESS+WS 加 TLS，会破坏 Host 免流语义）。

## 8. 排障手册

| 现象 | 排查顺序 |
|---|---|
| 客户端连不上 | ① `date` 核时（VMess ±120s 时间窗）→ ② `tail /tmp/xrayz.log` 看 access rejected / invalid request → ③ 端口与 pid（`netstat -lnp`）→ ④ `readlink /proc/<pid>/exe` 确认跑的是哪个二进制 |
| 连接能建立但无数据 | 看 access 行是否出现（出现＝已 dispatch，问题在出站/目标）；KCP 链路先看是否丢包严重 |
| 资源异常 | `grep selfcheck` 看 conns/threads/rss_kb/fd 趋势；fd 只增→连接未回收；rss 只增→查缓冲池 |
| 偶发卡死（历史问题） | 已在 M9 修复（futex 互斥锁孤儿等待者 + 会话线程 UAF）。若复现：打包机装 gdb，`gdb -p <pid> -batch -ex 'thread apply all bt'` 抓全线程栈 |
| 丢包环境短连接失败 | 属 mKCP 固有（见 §5 注），非本实现回归；对照上游同条件成功率判断 |
| **进程静默退出 / `Segmentation fault at address 0x…`** | 设备无 gdb，按此取 core：① `cd <二进制目录>` ② `( ulimit -c unlimited; nohup ./xrayz run -c xray.json >> /tmp/xrayz.log 2>&1 & )` ③ 复现 ④ core 落在 cwd ⑤ 传回打包机，`apt-get install gdb-multiarch`，`gdb-multiarch -batch -ex "bt 20" <带符号二进制> <core>`。**ReleaseSafe 产物默认 strip**，需用 `zig build -Dtarget=aarch64-linux-musl -Drelease -Dstrip=false` 构建带符号版；两次构建地址不同，务必用"同一份带符号二进制在设备上重跑复现"得到的 core |
| **UDP/QUIC 不通（历史）** | M19 之前服务端直接拒绝 UDP 命令、并把 mux 里的 UDP 帧当"未知网络"断整条 mux；M20 起走 XUDP over mux 真会话。排查：`grep "mux session opened.*dest_port=53" /tmp/xrayz.log` 应能看到 UDP 会话；看不到＝客户端没走 mux（检查客户端 `mux.xudpConcurrency`） |
| **线程数只增不减** | ① 先分清"活着"还是"泄漏"：`for t in /proc/$(pidof xrayz)/task/*; do cat $t/wchan; done \| sort \| uniq -c`——大量 `__skb_recv_datagram` = 正常活跃的 XUDP 会话（客户端 xudpConcurrency 保活）；② `grep -c "mux session opened"/"closed"` 对不上且 wchan 是 `hrtimer_nanosleep` = DownWriter 未退出（M20 已修：下行写侧必须半关闭） |
| mux 连接断开后崩溃（历史） | M18 已修：`link.writer` 属上层 arena，`serve` 必须阻塞等会话线程归零后才返回（原 DrainGuard 只等 sess_arena → DownWriter 写 End 帧时上层 arena 已释放 = UAF）。若复现，先看 core 栈是否 `DownWriter.writeEnd` ← `AuthWriter.writeAll` |

## 9. 通勤复盘 SOP（M28，用户报"上下班用着有问题"时按此做）

### 9.1 拉日志（设备无 python3 / 无 SFTP，走 SSH exec 通道）

设备（192.168.1.1:10022）只开 exec。两种拉法，**重定向到本地文件**（避免大输出被截断）：

```sh
# 主日志（当天全部，含轮转归档前的历史）
cat <<'SH' | python3 .temp/dev.py 180 > .temp/dev_full.log 2>&1
cat /tmp/xrayz.log
SH
# access 日志（按需）
cat <<'SH' | python3 .temp/dev.py 120 > .temp/dev_access.log 2>&1
cat /tmp/xrayz-access.log
SH
# 若已跨天/被归档：先看有哪些归档
cat <<'SH' | python3 .temp/dev.py 60
ls -la /tmp/xrayz.log* /tmp/xrayz-access.log*
SH
```

⚠️ **日志在 tmpfs，设备重启即丢**；cron 每日 04:00 归档一份（保留 14 份），
复盘越早做越好。**日志时间戳是 UTC**，比本地（CST）慢 8 小时。

### 9.2 生成复盘报告

```sh
python3 zig-src/tools/commute_report.py -f .temp/dev_full.log     [-a .temp/dev_access.log] --from '08:00' --to '09:30'
```

- `--from/--to` 给**本地时间**（`HH:MM` = 当天，或 `YYYY-MM-DD HH:MM`），工具自动换算 UTC 匹配；
- 报告七节：连接时长分布 / mux 会话配对 / KCP 重传统计 / 握手与错误 / overload 拒绝 /
  selfcheck 资源曲线 / access 目标聚合，末尾给分级诊断结论；
- **退出码 1 = 有"严重"级发现**（撞上限 / 重连风暴 / 疑似泄漏），可接自动化。

### 9.3 形态对照表（日志特征 → 结论）

| 用户体感 | 日志特征 | 结论 |
|---|---|---|
| 连不上 / 丢包严重 | 【5】overload 拒绝 >0 | 撞并发上限（M21 教训：客户端 mux 被拒后回退直连，连接数放大 10 倍） |
| 时快时慢 / 视频卡 | 【3】KCP retrans/sent 比例高 | 链路丢包（VMess+KCP 路径；需 M28+ 二进制才有此统计） |
| 频繁断连重连 | 【1】短命连接(<1s)率 >30% + 【4】握手失败多 | 重连风暴（弱网或服务端拒绝后的反复重试） |
| 越用越卡 / 会话变少 | 【2】mux opened-closed 差持续增大 | 会话泄漏/悬挂（M20 形态：下行未半关闭） |
| 某个 App 不通、其他正常 | 【4】`failed to open connection to <目标>` 集中 + 【7】access 目标聚合 | 目标站点不可达，非线路问题 |
| 整体变慢 | 【6】threads/fd 峰值高 + 【1】时长整体变长 | 资源压力或链路劣化，对照 selfcheck 曲线 |

### 9.4 复盘后的动作

- 严重级 → 先看报告第 4 节的 `e.g.` 样本行定位根因，再决定是否回滚二进制
  （`/opt/armbian/bin/xray/` 下有 `xrayz.mNN.bak` 备份链，`cp -a` 回切后 `xrayz-start.sh restart`）；
- 弱网类结论 → 用 `tools/kcp_loss.py` / `tools/ws_weaknet.py` 在打包机复现同档丢包对比；
- 需要留证据 → 复盘完成后把 `.temp/dev_full.log` 与报告输出存到项目 `zig-src/.review/`（勿只留 tmpfs）。
