## 2. 六个高风险区（必看）

### 2.1 futex 互斥锁 — `src/common/sys.zig:85`

**风险等级：最高**（错了就是全进程随机死锁，且难复现）

Zig 0.17 移除了 `std.Thread.Mutex`，`std.Io.Mutex` 需要 Io 实例，所以自研。

**M9 踩过的坑（已修，红线）**：初版用标准三态（0=空闲/1=持有/2=竞争）+ 解锁唤醒 1 个等待者。
被唤醒者抢锁失败重新睡下（state=2），而抢到锁者以 state==1 解锁（swap 得 1，不触发 wake）——
剩余等待者**永久睡死**。实机表现为 1MiB 下行约 1/3 概率永久卡死，gdb 现场是
写线程卡在 `SendingWorker.push` 的 lock 上、锁值恒为 2 却无持有者。

**当前实现**：musl 形态——`state` 只管持有、`waiters` 另计、解锁时**只唤醒 1 个等待者**（`WAKE` val=1），
等待者醒来后重新 `swap` 抢锁（期望值恒为 1），不存在丢失唤醒的窗口；等待本身带 1s 超时兜底，
任何残余异常都不会变成永久挂死。

**审核点**：`unlock` 是否"swap 得 1 且 `waiters>0`"才 `WAKE`；`lockSlow` 的 `waiters` 加减是否与 futex wait 配对
（`fetchAdd` 在循环外、`fetchSub` 在抢到锁后）；超时醒来是否重查状态而非直接放弃。

**验证**：`sys.zig` 内有 8 线程 × 2 万次并发回归；M9 之后互通 1MiB 连跑 6 轮 + soak 无卡死。

### 2.2 mux 会话生命周期 — `src/common/mux.zig:381`（`waitInflight`）、`:516`（`sessionMain`）、`:547`（`serve`）

**风险等级：最高**（错了是 use-after-free / SIGSEGV / 线程永久悬挂）

三个真实故障（M9–M20 陆续修掉，都是实机 SIGSEGV / 悬挂逼出来的）：

1. **`sessionMain` 收尾解引用已释放对象**（M9/M12 系列）：defer 是 LIFO，日志块若在 `mgr.leave()`
   之后执行，而 `leave()` 让 inflight 归零 → `serve` 的 `waitInflight` 返回并释放 `sess_arena`——
   **`job` 本身就在该 arena 内**，直接用 `job.id/job.dest` 就是 UAF（aarch64 ReleaseSafe 实测
   SIGSEGV：`mux session closed` 打印后立刻崩溃）。同类问题在 KCP 路径是 `defer inst.gpa.destroy(ta)`
   与解引用 `ta.instance` 的顺序（`instance.zig:319-345`）。
   **审核点**：所有 defer 块是否先把指针/字段快照到栈上（当前 `sessionMain` 开头快照了
   `job_id/job_dest_port/job_logger/started_ms` 四个量，就是为此）。
2. **`serve` 退出不等会话线程**（M20）：`link.writer` 是上层 arena 的对象，上层在 `serve` 返回后
   立刻 deinit。若还有 DownWriter 在 `writeEnd()` 里用它 → UAF。**当前做法**：`defer { closeAll(); waitInflight(); sess_arena.deinit(); }`，
   **必须阻塞等所有会话线程真正结束**，不能用「后台 drain」。
3. **收尾悬挂吃满并发上限**（M20）：UDP 下行漏了 `shutdownWrite` → DownWriter 在 `Pipe.read` 永久轮询 →
   该线程永不 `leave()` → `waitInflight` 永久阻塞 → 连接线程 + arena 泄漏 → 256 上限被僵尸连接吃满 →
   **新连接全被拒**（用户最初报的"丢包严重"就是这个形态）。**审核点**：`sessionMain` 退出前是否
   同时 `closeWrite` 上下行两条管道（不能只依赖出站层记得半关闭）。

**验证**：`tools/xudp_smoke.py` T4（SIGKILL 强杀后线程回落基线）、互通 I5（mux 10/10）、
设备侧 `mux session opened == closed` 计数配对。

### 2.3 双向拷贝模型与超时语义 — `src/proxy/freedom.zig:628/630`

**风险等级：高**（错了是会话永久阻塞或栈溢出）

**当前模型（M24/M26）**：只 spawn 下行线程，**上行拷贝在调用线程跑**（连接线程 / mux 出站线程）。
每连接 3→2 线程、XUDP 会话 4→3。

**两条红线（都是踩坑换来的）**：

1. **超时必须每轮重设，不能缓存**（M23）：WS 的 reader/writer 是同一个 Session、底层同一个 socket fd，
   上行设 1s（切片轮询）与下行设 threshold(300s) 会互相覆盖。一旦「只在变化时 setsockopt」，
   读超时被对方改成 300s → 会话永久阻塞（实测全量测试卡死在 117/166、162/166）。
2. **调用线程栈必须 ≥512KB**（M24）：`copyMain` 内含 32KB 栈缓冲 + 协议体编解码，64KB 栈会溢出。
   `dispatcher.zig` 三处测试原用 `min_thread_stack`（musl 64KB），已改 `crypto_thread_stack`。

**性能设计（M23）**：32KB 拷贝缓冲（原 8KB）。strace 实测（0% 丢包、一次 1MiB 下行）：
8KB 时 104 次 `recvfrom` + **569** 次 `setsockopt`（每 8KB 一轮设 4 次超时）；32KB 后降到
44 + 161，总 syscall 1054 → **339**，Go 为 390。代价是调用线程栈要放得下 32KB 缓冲（见上）。

**验证**：`tools/ws_weaknet.py`（弱网 1MiB 10 次中位数 3.70s vs Go 4.41s）、`tools/regress_all.py` 8/8。

### 2.4 KCP 状态机 — `src/transport/kcp/conn.zig:790`（`setState`）

**风险等级：高**（1189 行，最复杂；协议对时序敏感）

六个状态（`conn.zig:25`）：`active / ready_to_close / peer_closed / terminating / peer_terminating / terminated`，
状态迁移驱动的动作（`closeWrite`、`ping_interval` 切换、`forceTerminate`）必须与上游一致。

**M9 修掉的缺陷**：`setState(.terminated)` 漏了 `closeWrite()`（上游有）→ 会话收不到 EOF。
**M9/M20 修掉的生命周期问题**：Listener 单步 `close()` 的 UAF → 拆成 `shutdown()` / `deinit()`，
并加 `forceTerminate` + fd<0 保护。

**审核点**：
- `setState` 每个分支的动作是否与上游 `connection.go` 的 `setState` 一一对应；
- `flush` 的 terminating 早退 + `closeWrite` 清窗语义（这是"短连接尾包丢失"的根源，与上游同构，
  见 `tools/kcp_loss.py` 头部的 A/B 口径说明）；
- 重传/ACK 的窗口维护（`sending.processSegment`）与上游 `sending.go` 的差异。

**验证**：`tools/kcp_smoke.py`（T1 垃圾包/T2 建会话+ACK/T3 坏 AuthID→Terminate）、
`tools/kcp_loss.py` 0/5/10/20% 四档、互通 I4（VMess+KCP 1MiB sha256 连跑 6 轮）。

### 2.5 VMess AEAD 与分块体 — `src/proxy/vmess/aead.zig:81`（`openHeaderLength`）、`chunk.zig:39/49/159/286`、`inbound.zig`

**风险等级：高**（密码学，错一个字节就完全不通，且不会有"部分可用"）

**审核点**：
- AEAD 头（`aead.zig`）：线格式 `AuthID(16) || 密封长度(18=2B 密文+16B tag) || conn_nonce(8) || 密封载荷(N+16)`，
  `openHeaderLength` 的密封长度块布局与上游 `vmess/aead` 逐字节对齐；
- 分块体（`chunk.zig`）：SHAKE 掩码 + padding 长度（`shakePad`，读/写两侧各一）必须与上游 `chunk.go` 的
  `ReadSizeMask / WriteSizeMask` 序列一致——**这是互通的关键**，Go 客户端对不上就是全丢；
- 重放防护：`replay.zig` 的时间窗 + 会话历史（负向用例 I3 覆盖）。

**验证**：`tests/` 里有从上游移植的黄金向量逐字节锚定；互通 I2（VMess+WS）、I4（VMess+KCP）、
I3（坏 UUID 负向）；`tools/vmess_smoke.py` T1-T4（全链/坏 UUID/重放/SIGTERM）。

### 2.6 并发上限与连接入口 — `src/core/instance.zig`

**风险等级：中高**（配错了是"用户全断"，且日志看不出原因）

**M21 实机教训**：默认上限 64，地铁弱网下被触发 **7798 次**（7244 次来自同一手机）。
根因链：客户端 mux 被拒（`command 3` 2333 次）→ 回退直连 → 弱网重连风暴 → 连接数放大 10 倍 → 撞上限。
现默认 **256**，overload 日志带 `active=N`。

**审核点**：
- `acceptLoop` 是否"先判后加"（避免瞬时超额）；
- KCP 会话面（`onConn`）是否与 TCP 同规则；
- `connEntry` 的日志 defer 是否在 `conn.close()` 之前（否则打不出 duration）。

**验证**：`instance.zig` 内有并发上限单测；设备侧 `overload` 计数应为 0。

## 3. 已知偏差（与上游行为不同，已评估）

完整清单见 `交付说明.md` §6.1/§6.2，这里只列**审核时可能觉得"怪"的地方**：

| 位置 | 偏差 | 原因 |
|---|---|---|
| `mux.zig` DownWriter | 响应帧**一律 Keep**，从不发 New | 客户端 `handleStatusNew` 对带数据的帧直接 discard（M13 互通排障发现），发 New 会导致数据被丢 |
| `mux.zig` 退出路径 | 阻塞 `waitInflight`，不 detach | Zig 无 GC，`link.writer` 是上层 arena 对象，提前返回即 UAF（Go 能 detach 是靠 GC） |
| `freedom.zig` 超时 | 每轮 `setsockopt` | 共享 fd 竞态，缓存会导致永久阻塞（见 2.3） |
| `vless/inbound.zig`、`vmess/inbound.zig` | 拒绝裸 UDP 命令（仅 TCP/Mux） | 客户端 UDP 一律走 XUDP over mux（M20 已落地于 mux 路径），裸 UDP 命令无人使用；拒绝行为正确，但**告警文案 M19 时写过 "XUDP not implemented"，本轮已更正**（见 §2.7） |
| `common/buf.zig` | 池化上限 256 × 8KB | §3.5 内存红线；freedom 已改用 32KB 栈缓冲，不再依赖池 |
| 日志 | 关键节点新增 8 类日志（Info/Warning） | 排障必需（用户明确要求），上游没有；形态见设计文档 §7.5 表 7-2 |

## 6. 审核时最值得问的 5 个问题

1. `sys.Mutex` 的唤醒全部 + 超时兜底，是否覆盖了所有 futex 丢失唤醒的场景？（对照 §2.1）
2. `mux.serve` 的 `waitInflight` 无超时预算——若某个会话线程真的永不退出（例如 dial 挂死），
   整条 mux 连接会一直挂着。当前判断是"宁可挂着也不 UAF"，这个取舍是否接受？（对照 §2.2）
3. `freedom` 的"调用线程兼任上行拷贝"把线程数降了一半，但代价是**调用线程在会话期间不可复用**。
   对 KCP 会话线程（还要跑 20ms 定时器）是否会造成定时抖动？（当前未测出，但值得关注）
4. KCP 的 `maxSendingWindow` 仍是上游默认 2MB——设备 512MB 内存下，多会话叠加是否超 §3.5 红线？
   （设计文档已标为待评估项）
5. 弱网吞吐反超 Go 16% 的结论基于 `tc netem` + loopback；真实移动网络下 TCP 行为可能不同，
   是否需要在真机上做一次 A/B 再定论？
