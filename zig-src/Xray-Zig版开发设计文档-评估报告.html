四、突出优点

4.1 规范锚定纪律成熟

文档确立了「Go 源码即 single source of truth + 裁决顺序 + 禁止合理化改写」的总纪律。这是重写类项目不出偏差的生命线，而且它被写进了正文而非仅作口号——每个协议章节都以「对照上游哪一行」的方式展开。

4.2 范围控制精准

功能范围锚定到具体配置文件（xray.json）逐字段解读，不泛化到「完整 Xray」；「不实现清单」附带「触发时行为」，并明确「不支持即显式报错、仅遗留字段静默容忍」的边界原则——边界清晰，实施者没有发挥空间，也就没有偏差空间。

4.3 密码学方法论正确

KDF 这种闭包嵌套构造采用「先跑向量生成器、再向量驱动实现」的工作顺序；生成器与仓库同版本源码逐字对应且带自校验（AuthID CRC / 密封头往返 / 响应头 AEAD+CFB 往返全部 PASSED）。字节级正确性被向量锁定，而不是留给实现者「照着论文写」。

4.4 测试即门禁

上游测试逐个映射到函数名形成移植映射表，并禁止「先跑通再补测试」——测试与实现同步产生，避免重写项目最常见的「测试债务」。

4.5 有意偏差显式化（D1–D4）

每项与上游的有意偏差都有理由、有风险、有回归条件，并经业主确认。这种「偏差清单」文化在重写项目中极其重要——它把隐式漂移变成显式决策。

4.6 扩展机制清晰

用 comptime 注册表替代 Go init() 副作用导入协议，配三条防腐化纪律；数据面 walkthrough 细化到步骤级，可直接作为实施对照表。

五、问题清单（按严重级分级）

以下问题从「实施者视角」审查得出——即：一名工程师只拿着这份文档开工，会在哪里卡住或做错。

P0 建议修订后再交付实施团队（3 项）

P0-1　KCP Stream 的超时机制缺口（线程模型 × 传输实现的接缝）

涉及章节：§3.4 线程与内存预算 / §5.10 KCP 契约

文档称「空闲与超时全部用 SO_RCVTIMEO/SO_SNDTIMEO + 每操作刷新 deadline 实现，不需要独立定时器线程」——但 KCP 会话跑在 UDP 收包线程 + 有界队列之上，socket 超时对它无效。VLESS/VMess 的 60s 握手 deadline、300s idle 落到 KCP Stream 上时，必须依靠 condvar timed wait（§2.4 提到过，但未与 §3.4 缝合）或等价机制实现。这是文档内部两章之间的裂缝，实施者会直接卡住。

P0-2　预读「超读」（over-read）保留机制未设计

涉及章节：§5.7 VLESS 头读取 / §6.1 WS 传输

「一次性 8KB 预读」没有说明：预读缓冲区中超出协议头的载荷字节如何不丢失地进入后续 read 路径。Go 版靠 buf.MultiBuffer/BufferedReader 显式传递 first buffer；Zig 侧 Stream 接口只有 read/write，文档没有给出「预读缓冲」的载体设计或 reader 链设计。WS 的 0-RTT early data（Sec-WebSocket-Protocol 携带的首批字节）同样汇入此路，一并受影响。

P0-3　数据面分块体没有黄金向量

涉及章节：§5.8 VMess 数据面 / §7.2 密码学测试

现有黄金向量只覆盖头（KDF / 密封头 / 响应头），而 chunk.zig 的 nonce 计数器递增、SHAKE128 长度掩码（种子 = bodyIV）、auth_len 独立加密——这些才是 VMess 数据面字节级正确性的核心——反而没有向量锁定。建议附录 A 增加 ≥2 组连续分块向量（含掩码、含递增 nonce），否则数据面只能靠与 Go 客户端互通间接验证，单测门禁形同虚设。

P1 影响验收质量或运维确定性（4 项）

P1-1　无性能验收门禁

涉及章节：§7.4 验收 Checklist

Checklist 覆盖了功能、稳定性、体积，唯独没有「同设备同负载 Zig vs Go 对拍：RSS 峰值 / 启动时间 / 代理吞吐 / 每 MB CPU」。本次重写的动机就是资源敏感（体积大、启动内存高），不量化收益就无法向业主证明重写价值。建议 M6 前补充一组对拍指标作为验收项。

P1-2　时序测试方法论缺失

涉及章节：§7.1 测试映射表

文档只写「时序用例放宽为语义断言」，但 ±120s 时间窗、3 分钟防重放历史的可移植测试需要可注入时钟（TimeSource）。这应作为模块设计要求写进 §5（如 kdf/authid 模块接受时间源参数），而不是留给实施者自由发挥——否则这类测试要么被跳过，要么各写各的。

P1-3　VMess 握手 vs KCP 空闲竞争未点破

涉及章节：§5.10 KCP 契约

客户端 KCP 建连后若 >30s 不发数据，会被 KCP 30s 空闲判定先杀会话——这与上游行为一致、不算偏差，但文档未明示。实施者联调时极易把它当 bug 去「修」，反而制造了与上游的差异。建议在 KCP 章节以「已知竞态」形式注明。

P1-4　内存预算偏乐观

涉及章节：§3.4 内存预算表

预算未计入：线程 guard page（约 103 线程 ≈ 0.4MB）、musl 每线程 TLS/errno（约 1–2KB/线程）、分配器元数据、静态二进制 .bss/.data。设备真实空闲仅 5.9–8.7MB，而预算约 20MB，缺口全押「页缓存弹性」——匿名页一旦触碰即常驻。建议预算表补充「最坏常驻」口径列。

P2 引用与表述瑕疵（4 项）

P2-1　源码路径引用错误

位置：表 4-1（dialer 参数）

引用 common/internet/system_dialer.go，实际路径为 transport/internet/system_dialer.go（本仓库 common/internet/ 下无此文件）。

P2-2　KCP ping 描述含混

位置：表 5-6（KCP 定时器）

「ping 固定 5s 发 CommandPing（另每 3s 一个）」把两个定时器混为一谈：5s 是 pingUpdater 的唤醒周期（connection.go:243），3s 才是 CommandPing 实际发送间隔（connection.go:643-644）。照此实现会发出错误的 ping 节奏。

P2-3　R1 风险可补充威胁模型结论

位置：风险章节 R1

R1 提醒「不要擅自加 TLS」是对的，但建议补一句威胁模型结论：本形态（VLESS 明文 UUID + WS Host 伪装、mKCP 明文）不提供抗主动审查/流量识别能力——这是配置固有属性，应让业主知情决策，而非仅作操作提醒。

P2-4　交付现状宜明示

位置：§3.2 目录规划

zig-src/ 目录树（build.zig、src/、tests/）尚未创建，当前仅 3 份资产到位（xray.json、tools/gen_golden_vectors.go、tests/golden/vmess_aead.txt）。目录规划是「目标态」，宜在交付说明中注明，避免实施团队误判交付不完整。

六、修订建议与结论

修订优先级建议：

  1. 移交前（P0）：补齐三个接缝定义——KCP Stream 的 deadline 机制（condvar timed wait）、预读超读保留的接口/reader 链设计、数据面分块体黄金向量（≥2 组）。这三项都不需要改架构，属于「补定义」，工作量小、收益大。
  2. M0–M1 期间（P1）：验收 Checklist 增加 Zig vs Go 资源对拍项；§5 增加 TimeSource 可注入性设计要求；KCP 章节注明 30s 空闲与 VMess 握手的已知竞态；内存预算补「最坏常驻」口径。
  3. 随时（P2）：修正两处引用/表述错误；R1 补威胁模型结论；交付说明注明目录规划为目标态。
总结：本设计文档在技术事实准确性、范围纪律、契约意识、测试门禁四个维度都达到了很高水准——22 项源码抽查全部属实、引用行号基本准确，在上游重写类项目中属于少见的高质量文档。它的问题不是「写错了什么」，而是「少定义了三个关键接缝」和「验收缺资源量化维度」。按上述优先级修订后，即可作为实施依据正式移交给实施团队。
