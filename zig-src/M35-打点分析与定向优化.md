# M35：光猫生产打点分析 —— 客户端连接定向优化清单

> 数据源：设备 `192.168.1.1:10022`（F4610U 光猫 / Armbian 容器），现役进程 pid 6993，
> `/tmp/xrayz.log` 1.89MB。样本窗口 **2026-10-27 10:25:05 → 18:52:30（8.45h）**，
> 顶层连接 **2312 条**、mux 子会话 **259 条**。
>
> 打点口径已核对源码（`src/app/trace.zig`）：`ws_ms` 为自 accept 起绝对值，
> `hdr_wait/hdr_parse/dial_ms` 为相邻增量，`down_first(ttfb)` 为自 accept 起绝对值
> ⇒ **`ttfb ≈ ws + hdr_wait + hdr_parse + dial + 目标响应`**，可无损分解。

## 0. 一句话结论

服务端**不是瓶颈**。到处 optimizations 的主战场在**连接复用与失败快慢**，
其中"不可达目标被重试到 81 秒"这一项独占全部浪费的大头。

## 1. 服务端健康度（先排除）

| 指标 | 实测 | 判读 |
|---|---|---|
| `hdr_parse_ms` | avg **0.0ms** / max 1ms | 服务端探解析零成本，CPU 完全无压力 |
| `hdr_wait_ms` | avg **0.0ms** / max 8ms | 客户端发头很及时，无弱网首包重传 |
| 进程资源 | Threads **4** / VmRSS **5888 kB** | 极健康（M31 峰值 10.9MB，本窗口更轻） |
| `overload` | **0** 次 | 并发上限 256 从未撞到，不是限制因素 |
| `trace_stats conns` | 2312 / 8.45h | 约 274 连接/小时 |

**判据**：两个 cpu 相关stage 都 ≈0 ⇒ 无需在服务端做算法/缓冲优化，改什么都测不出收益。

## 2. 🔴 P0 —— 不可达目标被重试到 81 秒

这是本次唯一"独占大头"的浪费。

```
dial_fail 149 条（6.4%）
  拨号耗时  p50=81218ms  p90=81274ms  max=83836ms   ← 几乎全部贴满上限
```

**为什么恰好是 81 秒** —— 源码可对账（`src/proxy/freedom.zig:227-259`）：

```zig
const dial_timeout_ms: i64 = 16 * 1000;   // 单次 16s
const dial_attempts = 5;                  // 5 次
const dial_backoff_base_ms: u32 = 100;    // 退避 0/100/200/300/400 = 1s
```

`5 × 16s + 1s = 81s`，与实测 p50=81218ms **逐毫秒吻合**。

**失败目标分布**（全是本设备出口不可达的地址）：

| 目标 | 次数 |
|---|---|
| play.googleapis.com / android.googleapis.com / content-autofill… | **111**（Google 系） |
| node-*.speedtest.cn 各节点 | **32** |
| api.myip.com、www.google.com 等 | 6 |

**代价**：每条连接占住「线程 + fd + 并发槽」整整 81 秒。
149 × 81s ≈ **3.35 小时的槽位空转**，摊在 8.45h 窗口内。

**优化（原方案作废 + 实际采用）**：

> ⚠️ **本轮修正**：初版此处写"把 Google 系域名配成 `finalRules` 的 block"，**不可实现**。
> 核对 `src/conf/freedom.zig:27-33` 后确认，`FinalRule` 只有
> `action / network / port / ip(CIDR)` 四个维度，**没有域名字段**。
> 要按域名拦截必须先给 `finalRules` 增加 domain 匹配器，属新增功能而非调优，本轮不做。

实际改为：**新增可调拨号参数**（`dialTimeoutMs`），改编纂见 §9。

## 3. 🟠 P1 —— TTFB 200ms 的三段构成

```
ttfb          avg 200.0ms   p50=56   p90=220   p95=731   p99=2650   max=32819
 ├ ws_ms        67.1ms (33.6%)   p50=9    p95=117   p99=1988   max=3850
 ├ hdr_wait      0.0ms ( 0.0%)
 ├ hdr_parse     0.0ms ( 0.0%)
 ├ dial_ms      76.1ms (38.0%)   p50=14   p95=48    p99=1011   max=32503
 └ target_resp  56.8ms (28.4%)   p50=22   p90=78    p95=195
```

（样本 1757 条有下行首字节的连接）

**读法**：三段的性质完全不同 ——

- **`ws_ms` 双峰严重**（p50=9ms → p99=1988ms，跳了 200 倍）。服务端侧的 WS 握手上限
  是 `handshake_timeout_ms=4000`（`transport/websocket/server.zig:29`），p99 已贴到上限一半，
  说明**客户端侧链路在这一小撮时刻很差**（移动网切换/弱信号）。这部分服务端改不动，
  属于客户端 RTT 问题。
- **`dial_ms` p95=48ms 尚可，p99=1011ms** —— 含 DNS 解析。见 §4。
- **`target_resp` 56.8ms** —— 纯目标站 + TLS，不可优化。

**可落地的**：这 200ms 里**没有一段是服务端 CPU**（两段都 0.0ms）。所以唯一有效手段是
**减少新建连接数**（下一节），把 ws_ms 与 dial_ms 摊薄。

## 4. 🟠 P1 —— 每次连接都重新做 DNS，无缓存

`src/common/sock.zig:394 resolveV4()` 直接调 musl `getaddrinfo`，**进程内无任何缓存**。
调用点在 `dialWithRetry` 的**循环内部** ⇒ 一次失败拨号会重复解析 **5 次**。

设备的 `/etc/resolv.conf` 是 `nameserver 223.5.5.5`（公网 DNS），每次解析都要出网。

**优化**：加一层进程内 DNS TTL 缓存（建议 TTL 60~300s，哈希表 + 单调时钟过期）。
对本窗口：musl getaddrinfo 的往返直接从热路径消失，`dial_ms` 有机会向 p50=14ms → 个位数 ms 收敛；
失败路径少 4/5 的解析次数。

**注**：属**新增功能**，不是修 bug。上游 Xray 的 Go 版也没有进程内缓存（靠 Go runtime 的
resolver 与系统 nscd），改动前请确认能接受偏离上游。

## 5. 🟡 P2 —— 下行碎片写：50% 的写操作只承载 0.4% 的字节

```
下行总计  687.7 MB / 79539 次写
  大块连接(>=600B/块)  1203 条   684.8 MB   39258 次写  (49.4% 的写, 99.6% 的字节)
  小块连接( <600B/块)   977 条     2.9 MB   40281 次写  (50.6% 的写,  0.4% 的字节)
```

**根因**：`src/proxy/freedom.zig:715-724` 的拷贝循环是**读多少立刻写多少**，不做合并。
已有 8192B 的 `buf.Pool` 缓冲空闲着，但没有"攒够再发"的逻辑。

极端样本（纯浪费）：
```
down=359645  chunks=7091  每块 50B   tcp:node-58-246-202-134.speedtest.cn
```
7091 个 WS 帧承载 360KB。碎片最重的来源集中在
`speedtest.cn(28条/36213块)`、`imap.163.com`、`imap.189.cn`、`dig.bdurl.net`。

**优化**：下行加**读合并**——read 返回后，先非阻塞地把后续可用字节继续读入同一
8KB 缓冲，直到 buffer 接近满或 read 返回 WouldBlock 再 write 一次。
- 收益：这 50.6% 的写操作可压缩到约 1/10；客户端（手机）侧的收包处理次数同步下降。
- 风险：**会引入额外延迟**（等合并窗口），对本窗口 p50 的实时流（如 imap 长连接）
  不利，务必做成"只有检测到连续小包时才合并"的自适应策略，不可无条件开启。

## 6. 🟡 P2 —— mux 基本没被用起来

```
mux 子会话 259 条
启用 mux 的父连接 258 / 2312（11%）
单条连接承载子会话 avg=1.0  max=2
```

对比 M31 窗口（732 会话/723 连接）同样是 ~1.0 —— 说明**客户端侧实际上几乎没启用
多路复用**，或每次都新建主连接。

**优化（收益最大且零风险，但要动客户端配置）**：客户端开启 mux 复用后：
- 新建连接数下降 ⇒ §3 的 `ws_ms`(33.6%) 与 `dial_ms`(38.0%) 被大幅摊薄；
- 按 avg 1.0 → 理想 8~16 复用估算，TTFB 中的 ~130ms 可摊到单次 handshake。

## 手机端要不要改？**完全不用**

先把结论写在最前面，因为这决定了动这套东西的风险等级。

**需要手机同步改动的**，只有入站这四个身份要素：

| 要素 | 当前值 | 本次是否改动 |
|---|---|---|
| UUID | `de53e864-…` | **未动** |
| 端口 | 19001 / 19002 | **未动** |
| WS 路径 | `/free` | **未动** |
| WS Host | `ltetp.tv189.com` | **未动** |
| 协议 | VLESS(WS) / VMess(KCP) | **未动** |

本次两处改动都只在 **出站拨号侧**（设备自己怎么往外网连），属服务端的内部行为，
**不参与客户端握手，不影响任何入站身份校验**。手机上一条配置都不用碰。

改完后我用真实客户端流量做了 5 项验证（见下），全部通过。

## 改了什么

### ① 新增 `dialTimeoutMs` / `dialAttempts` 配置项（conf/freedom.zig）

关键设计：**默认值保持上游原样**，不配就等于没改。只在 `xray.json` 里显式调参。
这样以后想再调不用重新编译、不用再传二进制。

越界值（含 0）**静默回落默认并告警**，刻意不让它成为启动失败路径。

### ② 新增进程内 DNS 缓存（common/sock.zig）

- 128 条目上限、主机名 ≤96B、TTL **60s**
- **getaddrinfo 阻塞期间不持锁**（这点最关键：DNS 实测 p95 达 309ms，
  持锁会把所有待解析的连接串行化，比不缓存还糟）
- 拨号彻底失败时 `dnsInvalidate` 主动失效该域名（CDN 换 IP 的自愈兜底）

### ③ 为什么**没有**砍重试次数 —— 一条反向证据

原本想把 `dial_attempts` 从 5 砍到 3、耗时从 81s 压到 15s。查了成功拨号的分布后发现不能这么做：

```
成功拨号 dial_ms（n=2132）:  p50=13ms  p90=39ms  p95=66ms
                            p99=19061ms  p99.9=55485ms  max=79806ms
> 5s 的成功拨号: 37 条 (1.74%)
```

**max=79806ms 几乎贴满 81s 总预算** ⇒ 确有连接是靠**第 5 次**尝试才成功的。
把 attempts 砍到 3 会把这 1.74% 从"慢成功"扭成"失败"——是真实的体感倒退，不划算。

反之，**缩单次超时是安全的**：它不减少尝试次数，只是让每一次更快轮到下一次；
原本"第 N 次才连上"的依然能连上，只是更早。故采用超时减半、次数不变。

## ⚠️ 关于 DNS 缓存收益：如实说明，暂未宣称效果

上线后我用同一域名连发三次测 `dial_ms`，结果是 **40 / 38 / 36 ms**，
而改前同域名的历史值是 **43ms**。

趋势向下，但**幅度小、样本只有 3 条，落在噪声范围内，不足以证明收益**。
原因是该域名在运营商/上游 DNS 侧大概已经有缓存，没能代表那 12ms(p50)/309ms(p95)
的普遍 DNS 增量（那个数字是全量域名口径，见 §4）。

要真正确认 DNS 缓存的价值，需要拉一整天的新日志，用 §1 那套
「域名目标 vs IP 目标」的对照口径重新算一遍。**建议观察 1~2 天再判断**，
不要凭这三次测试下结论。
